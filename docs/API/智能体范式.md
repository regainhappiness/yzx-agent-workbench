## 第一部分：从 `.env` 环境变量中获取配置

### 1.1 为什么使用环境变量？

将 API 密钥、服务地址等敏感配置硬编码在代码中是危险的——一旦代码被提交到 Git 仓库，密钥就会泄露。使用 `.env` 文件 + 环境变量的方式可以：

- **安全性**：`.env` 文件加入 `.gitignore`，不会被提交到版本控制
- **灵活性**：不同环境（开发/测试/生产）可使用不同的 `.env` 文件
- **便捷性**：无需每次修改代码来切换配置

### 1.2 使用 `python-dotenv` 加载 `.env`

```python
from dotenv import load_dotenv

# 加载 .env 文件中的环境变量到 os.environ
load_dotenv()
```

`load_dotenv()` 默认查找当前工作目录下的 `.env` 文件，并将其中的键值对加载为环境变量。

### 1.3 `.env` 文件格式

```env
# 大语言模型 API 配置
LLM_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxx
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL_ID=deepseek-v4-pro
LLM_TIMEOUT=60
```

- 每行一条 `KEY=VALUE` 配置
- `#` 开头的行为注释
- 值不需要加引号（除非值本身包含空格或特殊字符）

### 1.4 使用 `os.getenv()` 读取配置

```python
import os

self.model = model or os.getenv("LLM_MODEL_ID")
apiKey = apiKey or os.getenv("LLM_API_KEY")
baseUrl = baseUrl or os.getenv("LLM_BASE_URL")
timeout = timeout or int(os.getenv("LLM_TIMEOUT", 60))
```

**优先级策略**：显式传参 > 环境变量 > 默认值。

`os.getenv("KEY", default)` 的第二个参数是回退默认值——当环境变量不存在时使用。例如 `os.getenv("LLM_TIMEOUT", 60)` 表示如果未设置 `LLM_TIMEOUT`，则默认超时时间为 60 秒。

### 1.5 配置校验

```python
if not all([self.model, apiKey, baseUrl]):
    raise ValueError("模型ID、API密钥和服务地址必须被提供或在.env文件中定义。")
```

使用 `all()` 一次性校验所有必填配置项，缺少任何一项都会立即抛出明确的错误提示，这是一种**快速失败（fail-fast）** 的最佳实践。

## 第二部分：解析大语言模型的流式响应

### 2.1 什么是流式响应？

大语言模型生成文本时是逐 token 输出的。调用方式分为两种：

| 模式 | `stream=False`（非流式） | `stream=True`（流式） |
|------|--------------------------|------------------------|
| 响应方式 | 等待完整生成后一次性返回 | 边生成边返回数据块（chunk） |
| 用户体验 | 需要等待，可能较久 | 实时逐字显示，感知延迟低 |
| 适用场景 | 后台批量处理 | 聊天对话、实时交互 |

### 2.2 开启流式响应

```python
response = self.client.chat.completions.create(
    model=self.model,
    messages=messages,
    temperature=temperature,
    stream=True,   # 关键：开启流式
)
```

当 `stream=True` 时，API 返回的是一个**可迭代的生成器**（generator），而非一次性返回的完整对象。

### 2.3 逐块解析流式数据

```python
collected_content = []
for chunk in response:                          # 遍历每个数据块
    if not chunk.choices:                       # 安全检查：跳过空 choices
        continue
    content = chunk.choices[0].delta.content or ""  # 提取 delta 中的内容
    print(content, end="", flush=True)          # 实时逐字打印
    collected_content.append(content)           # 收集内容片段
print()  # 流式输出结束后换行
return "".join(collected_content)               # 拼接为完整响应
```

**关键点解析**：

1. **`chunk.choices[0].delta.content`**：流式模式下，每个 chunk 的内容在 `delta` 字段中（而非 `message` 字段）。`delta` 表示增量——即本次新增的 token。

2. **`or ""`**：当 chunk 的 `delta.content` 为 `None` 时（某些 chunk 可能不含文本内容，如流结束信号），用空字符串替代，避免打印 `None`。

3. **`print(content, end="", flush=True)`**：
   - `end=""`：不换行，让 token 连续输出
   - `flush=True`：强制刷新缓冲区，确保每个 token 立即显示（而非等缓冲区满）

4. **`"".join(collected_content)"**：将所有 token 片段拼接成完整响应文本，供后续使用。

### 2.4 流式响应块的典型结构（OpenAI 规范）

理解每个 chunk 的内部结构是正确解析流式响应的关键。流式响应的核心区别在于：

- **非流式响应**：`response.choices[0].message.content` 包含**完整的响应文本**
- **流式响应**：`chunk.choices[0].delta.content` 只包含**本次新增的增量文本**

一个完整的流式响应通常由以下三个阶段的数据块组成：

#### 第一个块：角色声明（通常无内容）

```json
{
    "id": "chatcmpl-xxx",
    "object": "chat.completion.chunk",
    "created": 1717560000,
    "model": "gpt-3.5-turbo",
    "choices": [
        {
            "delta": {"role": "assistant"},
            "index": 0,
            "finish_reason": null
        }
    ]
}
```

> 第一个 chunk 的 `delta` 中只有 `role: "assistant"`，没有 `content` 字段。这就是为什么代码中需要 `or ""` 来处理 `content` 为 `None` 的情况。

#### 中间块：增量内容

```json
{
    "choices": [
        {
            "delta": {"content": "你好"},
            "index": 0,
            "finish_reason": null
        }
    ]
}
```

> 中间的 chunk 携带 `delta.content`，内容是本次新生成的 token。这些 token 需要按顺序拼接才能得到完整响应。

#### 最后一个块：生成结束信号

```json
{
    "choices": [
        {
            "delta": {},
            "index": 0,
            "finish_reason": "stop"
        }
    ]
}
```

> 最后一个 chunk 的 `delta` 为空对象 `{}`，`finish_reason` 变为 `"stop"`（也可能为 `"length"` 表示达到最大长度截断）。此时 `content` 为 `None`。

---

**三个阶段的对照总结**：

| 阶段 | `delta` 内容 | `finish_reason` | 说明 |
|------|-------------|-----------------|------|
| 首块 | `{"role": "assistant"}` | `null` | 声明角色，无文本内容 |
| 中间块 | `{"content": "xxx"}` | `null` | 逐 token 输出增量文本 |
| 末块 | `{}` | `"stop"` / `"length"` | 空 delta，标记生成结束 |

> **提示**：正确处理这三个阶段是流式解析的关键——首块和末块的 `content` 都为 `None`，必须用 `or ""` 跳过，否则会打印出 `None` 字符串。

### 2.5 流式 vs 非流式的数据结构差异

| 字段 | 非流式 (`stream=False`) | 流式 (`stream=True`) |
|------|--------------------------|------------------------|
| 响应文本位置 | `response.choices[0].message.content` | `chunk.choices[0].delta.content` |
| 响应类型 | 单个 `ChatCompletion` 对象 | 可迭代的 `ChatCompletionChunk` 生成器 |
| content 含义 | 完整响应文本 | 增量文本（本次新增的 token） |

### 2.6 异常处理

```python
try:
    response = self.client.chat.completions.create(...)
    # ... 处理流式响应
except Exception as e:
    print(f"❌ 调用LLM API时发生错误: {e}")
    return None
```

异常处理覆盖网络超时、API 限流、认证失败等情况，返回 `None` 让调用方能够优雅地处理失败场景，避免程序崩溃。

## 第三部分：智能体经典范式之 ReAct

### 3.1 什么是 ReAct？

**ReAct**（Reasoning + Acting）是一种经典的智能体范式，由 Yao et al. 在 2022 年提出。它的核心思想是让大语言模型在**推理（Thought）**和**行动（Action）**之间交替进行，并通过**观察（Observation）**获取外部反馈，形成一个闭环：

```
┌──────────┐     ┌──────────┐     ┌──────────────┐
│  Thought │ --> │  Action  │ --> │  Observation  │
│  思考推理  │     │  调用工具  │     │   工具返回结果  │
└──────────┘     └──────────┘     └──────────────┘
       ^                                  │
       └──────────────────────────────────┘
              循环直到得出最终答案
```

与普通 LLM 调用的区别在于：

| 对比维度 | 普通 LLM 调用 | ReAct 智能体 |
|---------|-------------|-------------|
| 能力范围 | 仅依赖模型内部知识 | 可调用外部工具获取实时信息 |
| 推理方式 | 单次输入 → 单次输出 | 多轮 Thought → Action → Observation 循环 |
| 适用场景 | 通用问答、文本生成 | 需要实时数据、多步推理的复杂任务 |

### 3.2 工具创建

在 ReAct 范式中，**工具（Tool）**是智能体与外部世界交互的桥梁。每个工具本质上是一个函数，接收字符串输入，返回字符串结果。

以实战中的 `SearchFromGoogle.py` 为例——一个基于 SerpApi 的网页搜索引擎工具：

```python
from serpapi import SerpApiClient

def search(query: str) -> str:
    """
    一个基于SerpApi的实战网页搜索引擎工具。
    它会智能地解析搜索结果，优先返回直接答案或知识图谱信息。
    """
    try:
        api_key = os.getenv("SERPAPI_API_KEY")
        if not api_key:
            return "错误：SERPAPI_API_KEY 未在 .env 文件中配置。"

        params = {
            "engine": "google",
            "q": query,
            "api_key": api_key,
            "gl": "cn",        # 国家代码
            "hl": "zh-cn",     # 语言代码
        }

        client = SerpApiClient(params)
        results = client.get_dict()

        # 智能解析：按优先级选择最有价值的返回结果
        if "answer_box_list" in results:
            return "\n".join(results["answer_box_list"])
        if "answer_box" in results and "answer" in results["answer_box"]:
            return results["answer_box"]["answer"]
        if "knowledge_graph" in results and "description" in results["knowledge_graph"]:
            return results["knowledge_graph"]["description"]
        if "organic_results" in results and results["organic_results"]:
            snippets = [
                f"[{i + 1}] {res.get('title', '')}\n{res.get('snippet', '')}"
                for i, res in enumerate(results["organic_results"][:3])
            ]
            return "\n\n".join(snippets)

        return f"对不起，没有找到关于 '{query}' 的信息。"

    except Exception as e:
        return f"搜索时发生错误: {e}"
```

**工具函数的设计规范**：

1. **统一签名**：所有工具都遵循 `tool(query: str) -> str` 的接口规范——输入是字符串，输出也是字符串。这使得工具执行器可以用统一的方式调用任何工具。

2. **健壮的错误处理**：工具内部捕获所有异常并返回错误描述字符串（而非抛出异常），确保智能体流程不会因工具调用失败而崩溃。

3. **智能结果解析**：不是简单返回原始 API 响应，而是按优先级提取用户最需要的信息——优先返回直接答案（answer_box），其次知识图谱描述，最后才是搜索结果摘要。这让大模型更容易理解和利用工具的返回值。

### 3.3 工具执行器：注册、管理与执行

`ToolExecutor` 是工具的管理中心，负责三大职责：**工具注册**、**工具管理**和**工具执行**。

```python
class ToolExecutor:
    """负责管理和执行工具。负责工具注册、工具管理和工具执行"""

    def __init__(self):
        self.tools: Dict[str, Dict[str, Any]] = {}

    def registerTool(self, name: str, description: str, func: callable):
        """向工具箱中注册一个新工具。"""
        if name in self.tools:
            print(f"警告：工具 '{name}' 已存在，将被覆盖。")
        self.tools[name] = {"description": description, "func": func}
        print(f"工具 '{name}' 已注册。")

    def getTool(self, name: str) -> callable:
        """根据名称获取一个工具的执行函数。"""
        return self.tools.get(name, {}).get("func")

    def getAvailableTools(self) -> str:
        """获取所有可用工具的格式化描述字符串。"""
        return "\n".join([
            f"- {name}: {info['description']}"
            for name, info in self.tools.items()
        ])
```

**设计要点解析**：

#### 3.3.1 工具注册（`registerTool`）

```python
tool_executor = ToolExecutor()
tool_executor.registerTool(
    "Search",
    "一个网页搜索引擎。当你需要回答关于时事、事实以及在你的知识库中找不到的信息时，应使用此工具。",
    search
)
```

每个工具注册时需要提供三个要素：

| 参数 | 说明 | 示例 |
|------|------|------|
| `name` | 工具的唯一标识符 | `"Search"` |
| `description` | 工具的功能描述，会写入 Prompt 供 LLM 理解 | `"一个网页搜索引擎..."` |
| `func` | 工具的执行函数 | `search`（函数引用） |

> **关键洞察**：`description` 是 LLM 决定是否调用该工具的唯一依据——描述越精确，LLM 选择工具的准确率越高。如有重名工具注册，会打印警告并覆盖旧工具，避免静默替换导致调试困难。

#### 3.3.2 工具管理（`getAvailableTools`）

```python
def getAvailableTools(self) -> str:
    return "\n".join([
        f"- {name}: {info['description']}"
        for name, info in self.tools.items()
    ])
```

这个方法将所有已注册工具的名称和描述格式化为字符串，注入到 ReAct Prompt 模板中，让 LLM 知道当前有哪些工具可用。

#### 3.3.3 工具执行（`getTool`）

```python
tool_function = self.tool_executor.getTool(tool_name)
observation = tool_function(tool_input) if tool_function else f"错误：未找到名为 '{tool_name}' 的工具。"
```

通过工具名称查找对应的函数引用并执行。如果工具不存在，返回描述性错误信息而非崩溃，保持流程的健壮性。

### 3.4 ReAct 智能体的编码实现

#### 3.4.1 整体架构

```
┌────────────────────────────────────────────────────┐
│                    ReActAgent                       │
│                                                     │
│  ┌──────────┐   ┌──────────────┐   ┌────────────┐  │
│  │  LLM     │   │  ToolExecutor│   │  Prompt     │  │
│  │  Client  │   │  (工具执行器)  │   │  Template   │  │
│  └────┬─────┘   └──────┬───────┘   └──────┬─────┘  │
│       │                │                   │        │
│       └────────────────┼───────────────────┘        │
│                        │                            │
│              ┌─────────▼──────────┐                 │
│              │  Thought → Action  │                  │
│              │  → Observation     │                  │
│              │  循环控制           │                  │
│              └────────────────────┘                 │
└────────────────────────────────────────────────────┘
```

`ReActAgent` 组合了三个核心组件：
- **LLM Client**：负责调用大模型进行推理和决策
- **ToolExecutor**：负责管理和执行外部工具
- **Prompt Template**：指导 LLM 按照 ReAct 格式输出

#### 3.4.2 Prompt 模板设计

Prompt 模板是 ReAct 智能体最关键的环节——它定义了 LLM 的"行为规范"：

```python
REACT_PROMPT_TEMPLATE = """
请注意，你是一个有能力调用外部工具的智能助手。

⚠️  最重要的规则：你的所有输出必须严格遵循以下格式，绝对不能有任何偏差！
⚠️  你必须先输出Thought或者Action，不能直接输出答案或JSON。
⚠️  当你收集到足够的信息，能够回答用户的最终问题时，你必须在`Action:`字段后使用 `Finish[最终答案]` 来输出最终答案。
⚠️  如果违反格式要求，系统将无法解析你的响应，导致任务失败

可用工具如下：
{tools}

请严格按照以下格式进行回应：
Thought: 你的思考过程，用于分析问题、拆解任务和规划下一步行动。
Action: 你决定采取的行动，必须是以下格式之一：
- `{{tool_name}}[{{tool_input}}]`：调用一个可用工具。
- `Finish[最终答案]`：当你认为已经获得最终答案时。
- 当你收集到足够的信息，能够回答用户的最终问题时，你必须在`Action:`字段后使用 `Finish[最终答案]` 来输出最终答案。

现在，请开始解决以下问题：
Question: {question}
History: {history}
"""
```

**Prompt 模板的关键设计要素**：

| 要素 | 说明 |
|------|------|
| **角色设定** | "有能力调用外部工具的智能助手"——明确告知 LLM 其能力边界 |
| **格式约束** | 用 `⚠️` 强调格式的重要性——LLM 必须输出可解析的结构化文本 |
| **工具列表** | `{tools}` 占位符在运行时会替换为 `getAvailableTools()` 的输出 |
| **输出规范** | 明确规定 `Thought:` 和 `Action:` 两个字段，以及 `tool_name[tool_input]` 和 `Finish[answer]` 两种 Action 格式 |
| **历史注入** | `{history}` 将前几轮的 Action 和 Observation 注入当前 prompt，形成上下文链 |

#### 3.4.3 ReActAgent 类

```python
class ReActAgent:
    def __init__(self, llm_client: HelloAgentsLLM, tool_executor: ToolExecutor, max_steps: int = 5):
        self.llm_client = llm_client
        self.tool_executor = tool_executor
        self.max_steps = max_steps   # 最大执行步数，防止无限循环
        self.history = []
```

核心方法 `run()` 实现 Thought → Action → Observation 主循环：

```python
def run(self, question: str):
    self.history = []
    current_step = 0

    while current_step < self.max_steps:
        current_step += 1

        # 1. 构建 Prompt：注入工具列表、用户问题、历史记录
        tools_desc = self.tool_executor.getAvailableTools()
        history_str = "\n".join(self.history)
        prompt = REACT_PROMPT_TEMPLATE.format(
            tools=tools_desc, question=question, history=history_str
        )

        # 2. 调用 LLM 获取推理结果
        messages = [{"role": "user", "content": prompt}]
        response_text = self.llm_client.think(messages=messages)
        if not response_text:
            print("错误：LLM未能返回有效响应。"); break

        # 3. 解析 LLM 输出，提取 Thought 和 Action
        thought, action = self._parse_output(response_text)

        # 4. 判断是否结束：如果 Action 是 Finish，提取最终答案
        if action.startswith("Finish"):
            final_answer = self._parse_action_input(action)
            return final_answer

        # 5. 解析工具名和输入参数，调用工具获取 Observation
        tool_name, tool_input = self._parse_action(action)
        tool_function = self.tool_executor.getTool(tool_name)
        observation = tool_function(tool_input) if tool_function \
            else f"错误：未找到名为 '{tool_name}' 的工具。"

        # 6. 将本轮 Action 和 Observation 记录到历史中
        self.history.append(f"Action: {action}")
        self.history.append(f"Observation: {observation}")

    print("已达到最大步数，流程终止。")
    return None
```

**主循环流程图**：

```
开始
  │
  ▼
┌─────────────────────┐
│ 构建 Prompt         │  tools + question + history
└────────┬────────────┘
         ▼
┌─────────────────────┐
│ 调用 LLM            │  llm_client.think()
└────────┬────────────┘
         ▼
┌─────────────────────┐
│ 解析输出            │  _parse_output() → (Thought, Action)
└────────┬────────────┘
         ▼
    Action = Finish? ──Yes──> 返回最终答案 ──> 结束
         │ No
         ▼
┌─────────────────────┐
│ 调用工具            │  tool_function(tool_input)
└────────┬────────────┘
         ▼
┌─────────────────────┐
│ 记录 Observation    │  写入 history
└────────┬────────────┘
         │
         ▼
   达到 max_steps? ──Yes──> 返回 None ──> 结束
         │ No
         └──> 回到"构建 Prompt"
```

#### 3.4.4 输出解析：正则表达式

LLM 输出的是自由文本，需要通过正则表达式从中提取结构化信息。`ReActAgent` 提供了三个解析方法：

**解析 Thought 和 Action**：

```python
def _parse_output(self, text: str):
    thought_match = re.search(r"Thought:\s*(.*?)(?=\nAction:|$)", text, re.DOTALL)
    action_match = re.search(r"Action:\s*(.*?)$", text, re.DOTALL)

    thought = thought_match.group(1).strip() if thought_match else None
    action = action_match.group(1).strip() if action_match else None
    return thought, action
```

- `Thought:` 从行首匹配到 `Action:` 或文本末尾为止
- `Action:` 从行首匹配到文本末尾
- `re.DOTALL` 让 `.` 匹配包括换行符在内的任意字符

**解析工具调用**：

```python
def _parse_action(self, action_text: str):
    match = re.match(r"(\w+)\[(.*)\]", action_text, re.DOTALL)
    return (match.group(1), match.group(2)) if match else (None, None)
```

将 `"Search[华为最新手机]"` 解析为 `("Search", "华为最新手机")`。

**解析最终答案**：

```python
def _parse_action_input(self, action_text: str):
    match = re.match(r"\w+\[(.*)\]", action_text, re.DOTALL)
    return match.group(1) if match else ""
```

将 `"Finish[华为最新手机是...]"` 解析为 `"华为最新手机是..."`。

#### 3.4.6 关键设计决策

| 决策 | 实现方式 | 原因 |
|------|---------|------|
| **防止无限循环** | `max_steps=5` | LLM 可能反复调用工具而无法收敛，设置上限避免消耗和死循环 |
| **历史注入** | 每轮将 Action 和 Observation 追加到 history | LLM 是无状态的——每次调用都需要将完整上下文传入 |
| **健壮的错误处理** | 工具未找到、输出解析失败等情况均不崩溃，记录错误继续循环 | 智能体应具备容错能力，偶尔的解析失败不应终止整个任务 |
| **正则而非 JSON** | 用正则表达式解析自由文本 | LLM 输出自由文本的成功率远高于输出严格 JSON；正则更宽容 |

## 第四部分：智能体经典范式之 Plan-and-Solve

### 4.1 什么是 Plan-and-Solve？

**Plan-and-Solve**（先规划后执行）是一种与 ReAct 互补的智能体范式。它的核心思想是**将推理和行动分离为两个独立的阶段**：

1. **规划阶段（Plan）**：由 Planner 将复杂问题一次性分解为多个有序的简单子任务
2. **执行阶段（Solve）**：由 Executor 按顺序逐个执行每个子任务，每步执行时都能看到历史结果

```
┌──────────────┐     ┌──────────────────────────────────┐
│   Planner    │ --> │  计划: [步骤1, 步骤2, 步骤3, ...]  │
│  生成计划     │     └──────────────────────────────────┘
└──────────────┘                      │
                                      ▼
                            ┌──────────────────┐
                            │    Executor      │
                            │  逐步执行计划      │
                            │                  │
                            │  步骤1 → 结果1    │
                            │  步骤2 → 结果2    │
                            │  步骤3 → 结果3    │
                            │  ...             │
                            └────────┬─────────┘
                                     ▼
                              最终答案
```

### 4.2 Plan-and-Solve vs ReAct 对比

| 对比维度 | ReAct | Plan-and-Solve |
|---------|-------|----------------|
| **核心流程** | 思考→行动→观察，多轮交替循环 | 先一次性规划，再逐步执行 |
| **决策时机** | 每步根据观察结果动态决策下一步 | 开始执行前完成全局规划 |
| **工具调用** | 每步可调用外部工具并观察结果 | 每步纯 LLM 推理，不调用外部工具 |
| **LLM 调用次数** | 不确定（取决于工具调用轮数，有 max_steps 上限） | 1 次规划 + N 次执行（N = 计划步数） |
| **适用场景** | 需要外部信息检索、实时数据查询 | 数学推理、逻辑分解、多步推导 |
| **优势** | 灵活，能根据环境反馈实时调整 | 思路清晰，不会偏离目标 |
| **劣势** | LLM 可能不遵循格式，导致解析失败 | 计划质量决定最终结果，缺乏纠错机制 |

> **关键洞察**：ReAct 适合"外部依赖"型任务（搜索、查天气），Plan-and-Solve 适合"内部推导"型任务（数学计算、逻辑推理）。实际应用中两者常结合使用。

### 4.3 规划器（Planner）实现

Planner 的职责是接收一个复杂问题，输出一个按逻辑顺序排列的步骤列表。

#### 4.3.1 Planner Prompt 模板

```python
PLANNER_PROMPT_TEMPLATE = 
"""
你是一个顶级的AI规划专家。你的任务是将用户提出的复杂问题分解成一个由多个简单步骤组成的行动计划。
请确保计划中的每个步骤都是一个独立的、可执行的子任务，并且严格按照逻辑顺序排列。
你的输出必须是一个Python列表，其中每个元素都是一个描述子任务的字符串。

问题: {question}

请严格按照以下格式输出你的计划，```python与```作为前后缀是必要的:

```python
["步骤1", "步骤2", "步骤3", ...]

"""
```


**设计要点**：

| 要素 | 说明 |
|------|------|
| **角色设定** | "顶级的AI规划专家"——让 LLM 专注于拆解和规划，而非执行 |
| **输出格式约束** | 要求输出 Python 列表字面量，用 ` ```python ` 包裹，便于 `ast.literal_eval` 安全解析 |
| **简洁性** | 每个步骤用一句话描述，保持计划清晰可读 |

#### 4.3.2 Planner 类

```python
class Planner:
    def __init__(self, llm_client: HelloAgentsLLM):
        self.llm_client = llm_client

    def plan(self, question: str) -> list[str]:
        prompt = PLANNER_PROMPT_TEMPLATE.format(question=question)
        messages = [{"role": "user", "content": prompt}]

        print("--- 正在生成计划 ---")
        response_text = self.llm_client.think(messages=messages) or ""
        print(f"✅ 计划已生成:\n{response_text}")

        try:
            # 从 ```python ... ```代码块中提取计划列表
            plan_str = response_text.split("```python")[1].split("```")[0].strip()
            plan = ast.literal_eval(plan_str)
            return plan if isinstance(plan, list) else []
        except (ValueError, SyntaxError, IndexError) as e:
            print(f"❌ 解析计划时出错: {e}")
            print(f"原始响应: {response_text}")
            return []
        except Exception as e:
            print(f"❌ 解析计划时发生未知错误: {e}")
            return []
```

**核心解析逻辑**：

```python
plan_str = response_text.split("```python")[1].split("```")[0].strip()
plan = ast.literal_eval(plan_str)
```

1. **`split("```python")[1]`**：提取第一个 Python 代码块之后的内容
2. **`split("```")[0]`**：取到代码块结束标记之前的内容
3. **`ast.literal_eval()`**：安全地将字符串解析为 Python 列表（比 `eval()` 安全，只解析字面量）

> **安全提示**：`ast.literal_eval()` 只解析 Python 字面量（字符串、数字、列表、字典等），不会执行任意代码，是处理 LLM 输出的安全选择。

**示例输入输出**：

```
输入: "一个水果店周一卖出了15个苹果。周二卖出的苹果数量是周一的两倍。周三卖出的数量比周二少了5个。请问这三天总共卖出了多少个苹果？"

输出计划:
["计算周二的销售数量：15 × 2", "计算周三的销售数量：周二数量 - 5", "计算三天总销量：周一 + 周二 + 周三"]
```

### 4.4 执行器（Executor）实现

Executor 的职责是按照 Planner 生成的计划，逐步执行每个子任务，并将历史结果传递给后续步骤。

#### 4.4.1 Executor Prompt 模板

```python
EXECUTOR_PROMPT_TEMPLATE = """
你是一位顶级的AI执行专家。你的任务是严格按照给定的计划，一步步地解决问题。
你将收到原始问题、完整的计划、以及到目前为止已经完成的步骤和结果。
请你专注于解决"当前步骤"，并仅输出该步骤的最终答案，不要输出任何额外的解释或对话。

# 原始问题:
{question}

# 完整计划:
{plan}

# 历史步骤与结果:
{history}

# 当前步骤:
{current_step}

请仅输出针对"当前步骤"的回答:
"""
```

**设计要点**：

| 要素 | 说明 |
|------|------|
| **角色设定** | "顶级AI执行专家"——让 LLM 专注于计算和输出，而非继续规划 |
| **四部分输入** | 原始问题（保持目标清晰）+ 完整计划（上下文）+ 历史结果（依赖数据）+ 当前步骤（焦点） |
| **输出约束** | "仅输出该步骤的最终答案，不要输出任何额外的解释或对话"——确保结果干净，便于后续步骤引用 |

#### 4.4.2 Executor 类

```python
class Executor:
    def __init__(self, llm_client: HelloAgentsLLM):
        self.llm_client = llm_client

    def execute(self, question: str, plan: list[str]) -> str:
        history = ""
        final_answer = ""

        print("\n--- 正在执行计划 ---")
        for i, step in enumerate(plan, 1):
            print(f"\n-> 正在执行步骤 {i}/{len(plan)}: {step}")
            prompt = EXECUTOR_PROMPT_TEMPLATE.format(
                question=question,
                plan=plan,
                history=history if history else "无",
                current_step=step
            )
            messages = [{"role": "user", "content": prompt}]

            response_text = self.llm_client.think(messages=messages) or ""

            # 累加历史：记录每一步的步骤描述和执行结果
            history += f"步骤 {i}: {step}\n结果: {response_text}\n\n"
            final_answer = response_text
            print(f"✅ 步骤 {i} 已完成，结果: {final_answer}")

        return final_answer
```

**执行流程解析**：

1. **初始化**：`history` 为空字符串，`final_answer` 为空
2. **逐步遍历**：`for i, step in enumerate(plan, 1)` 按顺序遍历计划中的每个步骤
3. **构建上下文**：每步都将 `question`（原始问题）、`plan`（完整计划）、`history`（已完成步骤的结果）注入 Prompt
4. **执行当前步骤**：调用 LLM 获取该步骤的结果
5. **记录历史**：将本步骤描述和结果追加到 `history`，供后续步骤参考
6. **最终输出**：最后一步的结果即为最终答案

**历史累加示例**：

```
步骤 1: 计算周二的销售数量：15 × 2
结果: 周二卖出30个苹果

步骤 2: 计算周三的销售数量：周二数量 - 5
结果: 周三卖出25个苹果

步骤 3: 计算三天总销量：周一 + 周二 + 周三
结果: 15 + 30 + 25 = 70个苹果
```

每一步都能看到前几步的计算结果，形成链式推理，避免了 LLM 在多步计算中"跳跃推理"导致的错误。

### 4.5 智能体（Agent）整合

`PlanAndSolveAgent` 将 Planner 和 Executor 组合为一个完整的智能体：

```python
class PlanAndSolveAgent:
    def __init__(self, llm_client: HelloAgentsLLM):
        self.llm_client = llm_client
        self.planner = Planner(self.llm_client)
        self.executor = Executor(self.llm_client)

    def run(self, question: str):
        print(f"\n--- 开始处理问题 ---\n问题: {question}")

        # 阶段一：规划
        plan = self.planner.plan(question)
        if not plan:
            print("\n--- 任务终止 --- \n无法生成有效的行动计划。")
            return

        # 阶段二：执行
        final_answer = self.executor.execute(question, plan)
        print(f"\n--- 任务完成 ---\n最终答案: {final_answer}")
```

**两阶段分离的优势**：

```
                    PlanAndSolveAgent
                    │
    ┌───────────────┼───────────────┐
    │               │               │
    ▼               │               ▼
阶段一：规划        │         阶段二：执行
    │               │               │
    ▼               │               ▼
Planner.plan()      │       Executor.execute()
    │               │               │
    ▼               │               ▼
[步骤1, 步骤2, ...]  │        逐步执行 → 最终答案
    │               │
    └───────────────┘
         各自独立，职责清晰
```

1. **职责分离**：Planner 只负责规划，Executor 只负责执行，各司其职
2. **失败隔离**：Plan 解析失败不会影响 Executor（提前返回）
3. **可替换性**：可以独立升级 Planner（如使用更强的模型）或 Executor（如加入工具调用能力）
4. **可观测性**：每个阶段的输出都清晰可见，便于调试和优化

#### 4.5.1 完整使用示例

```python
if __name__ == '__main__':
    try:
        llm_client = HelloAgentsLLM()
        agent = PlanAndSolveAgent(llm_client)
        question = "一个水果店周一卖出了15个苹果。周二卖出的苹果数量是周一的两倍。周三卖出的数量比周二少了5个。请问这三天总共卖出了多少个苹果？"

    except ValueError as e:
        print(e)
```

### 4.6 关键设计决策

| 决策 | 实现方式 | 原因 |
|------|---------|------|
| **两阶段分离** | Planner + Executor 独立类 | 职责清晰，可独立优化和调试 |
| **Python 列表作为计划格式** | `ast.literal_eval` 解析 | 结构化输出便于程序处理；`ast` 比 `eval` 安全 |
| **历史累加** | 字符串拼接 `history += ...` | 每步执行都能参考前序结果，形成链式推理 |
| **仅输出步骤答案** | Prompt 中约束"不要输出任何额外的解释" | 避免 LLM 输出冗余内容，确保结果干净可复用 |
| **无工具调用** | Executor 纯 LLM 推理 | Plan-and-Solve 擅长内部推导型任务，工具调用可留待 ReAct 或混合方案 |

### 4.7 Plan-and-Solve 与 ReAct 选择指南

```
需要调用外部工具？
    │
    ├── 是 ──> 需要多轮动态决策？
    │              │
    │              ├── 是 ──> ReAct
    │              └── 否 ──> 考虑 ReAct + Plan-and-Solve 混合
    │
    └── 否 ──> 问题可分步推导？
                   │
                   ├── 是 ──> Plan-and-Solve
                   └── 否 ──> 直接用 LLM 单次回答
```

> **实践建议**：对于复杂任务，可先用 Plan-and-Solve 生成全局计划，然后在 Executor 的每一步中嵌入 ReAct 式工具调用——这就是"Plan-then-Act"或"Plan-Act-Observe"混合模式的基本思路。

## 第五部分：智能体经典范式之 Reflection

### 5.1 什么是 Reflection？

**Reflection**（反思优化）是一种让 LLM 通过"自我审视—迭代改进"来持续提升输出质量的智能体范式。与 ReAct 和 Plan-and-Solve 不同，Reflection 不依赖外部工具或多步规划，而是通过一个**生成 → 审查 → 优化**的闭环来驱动输出不断进化。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   初始执行     │ --> │   反思评审     │ --> │   优化改进     │
│  (Generate)  │     │  (Reflect)   │     │  (Refine)    │
└──────────────┘     └──────────────┘     └──────────────┘
       ^                                          │
       │          ┌──────────────┐                │
       └──────────│   记忆模块     │<───────────────┘
                  │  (Memory)    │
                  └──────────────┘
              循环直到"无需改进"或达到最大迭代次数
```

**三种范式的定位对比**：

| 范式 | 核心问题 | 核心机制 | 典型场景 |
|------|---------|---------|---------|
| **ReAct** | "我需要什么信息？" | 思考→工具调用→观察→循环 | 搜索、查询、信息检索 |
| **Plan-and-Solve** | "我该分几步做？" | 规划→逐步执行 | 数学推导、逻辑分解 |
| **Reflection** | "我做得够好吗？" | 生成→评审→优化→循环 | 代码生成、写作润色、方案完善 |

> **关键洞察**：Reflection 的核心价值在于引入了一个"评审员"角色来评判输出质量，形成自我纠错的正反馈循环。它本质上是一种**测试时计算（test-time compute）**策略——通过额外增加推理轮次来换取更高质量的输出。

### 5.2 记忆模块（Memory）

Reflection 的核心基础设施是**记忆模块**——它存储智能体的执行轨迹和反思记录，使得后续迭代能够"看到"历史经验。

```python
class Memory:
    """一个简单的短期记忆模块，用于存储智能体的行动与反思轨迹。"""

    def __init__(self):
        self.records: List[Dict[str, Any]] = []

    def add_record(self, record_type: str, content: str):
        """向记忆中添加一条新记录。"""
        self.records.append({"type": record_type, "content": content})
        print(f"📝 记忆已更新，新增一条 '{record_type}' 记录。")

    def get_trajectory(self) -> str:
        """将所有记忆记录格式化为一个连贯的字符串文本，用于构建提示词。"""
        trajectory = ""
        for record in self.records:
            if record['type'] == 'execution':
                trajectory += f"--- 上一轮尝试 (代码) ---\n{record['content']}\n\n"
            elif record['type'] == 'reflection':
                trajectory += f"--- 评审员反馈 ---\n{record['content']}\n\n"
        return trajectory.strip()

    def get_last_execution(self) -> str:
        """获取最近一次的执行结果。"""
        for record in reversed(self.records):
            if record['type'] == 'execution':
                return record['content']
        return None
```

**设计要点**：

| 方法 | 职责 | 关键实现 |
|------|------|---------|
| `add_record(type, content)` | 追加一条新记录 | `type` 区分为 `'execution'`（代码）和 `'reflection'`（反馈） |
| `get_trajectory()` | 获取完整历史轨迹 | 按记录类型添加标签，便于后续 Prompt 构建 |
| `get_last_execution()` | 获取最近执行结果 | 用 `reversed()` 倒序查找，拿到最新的 `'execution'` 记录 |

**Memory 的数据结构**（内容示例）：

```python
[
    {"type": "execution", "content": "def find_primes(n):\n    primes = []\n    for num in range(2, n+1):\n        ..."},
    {"type": "reflection", "content": "该代码使用试除法判断素数，时间复杂度为 O(n√n)。建议使用埃拉托斯特尼筛法..."},
    {"type": "execution", "content": "def find_primes(n):\n    sieve = [True] * (n+1)\n    for p in range(2, int(n**0.5)+1):\n        ..."},
]
```

> **设计思路**：Memory 本质是一个带类型标签的列表。每条记录包含 `type`（区分执行/反思）和 `content`（具体内容）。这种简单的设计足以支撑 Reflection 的全流程，复杂场景下可扩展为向量数据库等持久化方案。

### 5.3 初始执行（Initial Generation）

Reflection 的起点是生成一个初始输出。这一步与普通的 LLM 单次调用相同，但输出会被存入 Memory。

```python
INITIAL_PROMPT_TEMPLATE = """
你是一位资深的Python程序员。请根据以下要求，编写一个Python函数。
你的代码必须包含完整的函数签名、文档字符串，并遵循PEP 8编码规范。

要求: {task}

请直接输出代码，不要包含任何额外的解释。
"""
```

**Prompt 设计特点**：

- **角色设定**："资深Python程序员"——限定输出风格和专业水准
- **明确规范**：完整的函数签名、文档字符串、PEP 8——设定质量基线
- **纯净输出**："不要包含任何额外的解释"——让 LLM 只输出代码，便于后续直接使用

```python
# 在 ReflectionAgent.run() 中的调用：
initial_prompt = INITIAL_PROMPT_TEMPLATE.format(task=task)
initial_code = self._get_llm_response(initial_prompt)
self.memory.add_record("execution", initial_code)
```

### 5.4 反思（Reflection）

反思阶段引入一个**专门的评审员角色**，对最新生成的代码进行严格的算法效率审查。

```python
REFLECT_PROMPT_TEMPLATE = """
你是一位极其严格的代码评审专家和资深算法工程师，对代码的性能有极致的要求。
你的任务是审查以下Python代码，并专注于找出其在**算法效率**上的主要瓶颈。

# 原始任务:
{task}

# 待审查的代码:
{code}


请分析该代码的时间复杂度，并思考是否存在一种**算法上更优**的解决方案来显著提升性能。
如果存在，请清晰地指出当前算法的不足，并提出具体的、可行的改进算法建议（例如，使用筛法替代试除法）。
如果代码在算法层面已经达到最优，才能回答"无需改进"。

请直接输出你的反馈，不要包含任何额外的解释。
"""
```

**反思 Prompt 的设计精髓**：

| 设计要素 | 具体实现 | 目的 |
|---------|---------|------|
| **角色反差** | "极其严格的代码评审专家" vs 初始的"资深程序员" | 用不同视角发现盲点 |
| **聚焦范围** | "专注于算法效率" | 避免评审过于分散，聚焦可优化点 |
| **具体引导** | "使用筛法替代试除法" | 给 LLM 提供具体的优化方向示例 |
| **终止条件** | "只有达到最优才能回答'无需改进'" | 设置明确的停止信号，防止过度优化 |

```python
# 在 ReflectionAgent.run() 中的调用：
last_code = self.memory.get_last_execution()
reflect_prompt = REFLECT_PROMPT_TEMPLATE.format(task=task, code=last_code)
feedback = self._get_llm_response(reflect_prompt)
self.memory.add_record("reflection", feedback)
```

### 5.5 优化迭代（Refinement）

当评审员指出不足后，进入优化阶段——让 LLM 结合反馈重新生成改进后的代码。

```python
REFINE_PROMPT_TEMPLATE = """
你是一位资深的Python程序员。你正在根据一位代码评审专家的反馈来优化你的代码。

# 原始任务:
{task}

# 你上一轮尝试的代码:
{last_code_attempt}

# 评审员的反馈:
{feedback}

请根据评审员的反馈，生成一个优化后的新版本代码。
你的代码必须包含完整的函数签名、文档字符串，并遵循PEP 8编码规范。
请直接输出优化后的代码，不要包含任何额外的解释。
"""
```

**优化 Prompt 的三部分输入**：

1. **原始任务**（`task`）：防止优化过程中偏离原始目标
2. **上一轮代码**（`last_code_attempt`）：让 LLM 知道改进的起点
3. **评审反馈**（`feedback`）：明确指出需要改进的方向

**迭代终止条件**：

```python
# 检查是否需要停止
if "无需改进" in feedback or "no need for improvement" in feedback.lower():
    print("\n✅ 反思认为代码已无需改进，任务完成。")
    break
```

> **注意**：此处使用关键词匹配来检测终止条件——简单但有效。在更复杂的场景中可让 LLM 输出 JSON 判断标记，或用函数调用来判断是否已收敛。

### 5.6 智能体（Agent）整合

`ReflectionAgent` 将 Memory、初始执行、反思和优化整合为一个闭环：

```python
class ReflectionAgent:
    def __init__(self, llm_client, max_iterations=3):
        self.llm_client = llm_client
        self.memory = Memory()
        self.max_iterations = max_iterations  # 最大迭代次数

    def run(self, task: str):
        print(f"\n--- 开始处理任务 ---\n任务: {task}")

        # --- 阶段一：初始执行 ---
        initial_prompt = INITIAL_PROMPT_TEMPLATE.format(task=task)
        initial_code = self._get_llm_response(initial_prompt)
        self.memory.add_record("execution", initial_code)

        # --- 阶段二：迭代循环：反思与优化 ---
        for i in range(self.max_iterations):
            # a. 反思
            last_code = self.memory.get_last_execution()
            reflect_prompt = REFLECT_PROMPT_TEMPLATE.format(
                task=task, code=last_code
            )
            feedback = self._get_llm_response(reflect_prompt)
            self.memory.add_record("reflection", feedback)

            # b. 检查终止条件
            if "无需改进" in feedback:
                break

            # c. 优化
            refine_prompt = REFINE_PROMPT_TEMPLATE.format(
                task=task, last_code_attempt=last_code, feedback=feedback
            )
            refined_code = self._get_llm_response(refine_prompt)
            self.memory.add_record("execution", refined_code)

        final_code = self.memory.get_last_execution()
        print(f"\n--- 任务完成 ---\n最终生成的代码:\n{final_code}")
        return final_code

    def _get_llm_response(self, prompt: str) -> str:
        """辅助方法，调用LLM并获取完整的流式响应。"""
        messages = [{"role": "user", "content": prompt}]
        response_text = self.llm_client.think(messages=messages) or ""
        return response_text
```

**完整的执行流程图**：

```
开始
  │
  ▼
┌──────────────────────────┐
│ 初始执行 (INITIAL_PROMPT) │  第 0 轮：生成初版代码
│ → 存入 Memory            │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│    迭代循环 (最多N轮)      │
│                          │
│  ┌────────────────────┐  │
│  │ 反思 (REFLECT_PROMPT)│  │  获取最新代码 → 评审
│  │ → 反馈存入 Memory   │  │
│  └────────┬───────────┘  │
│           │              │
│    反馈含"无需改进"？      │

```

def find_primes(n: int) -> list:
    """使用埃拉托斯特尼筛法找出1到n之间的所有素数。"""
    if n < 2:
        return []
    sieve = [True] * (n + 1)
    sieve[0] = sieve[1] = False
    for p in range(2, int(n ** 0.5) + 1):
        if sieve[p]:
            for multiple in range(p * p, n + 1, p):
                sieve[multiple] = False
    return [i for i in range(2, n + 1) if sieve[i]]

### 5.7 关键设计决策

| 决策 | 实现方式 | 原因 |
|------|---------|------|
| **评审与执行角色分离** | 两个不同的 Prompt 模板 | 不同视角（批评 vs 建设）更易发现盲点 |
| **Memory 模块** | 带类型标签的列表 | 存储完整轨迹，支持任意步骤回溯 |
| **关键词检测终止** | `"无需改进" in feedback` | 简单可靠，避免不必要的 LLM 调用 |
| **max_iterations 保护** | 最多 2-3 轮迭代 | 防止无限循环，平衡质量与调用成本 |
| **每次只评审最新代码** | `get_last_execution()` | 聚焦当前问题，避免评审历史包袱 |
| **三阶段分离** | INITIAL → REFLECT → REFINE | 每个 Prompt 职责单一，易于独立优化 |

### 5.8 三种范式的协同关系

```
Reflection 可与前两种范式灵活组合：

ReAct + Reflection
  │  在工具调用循环中嵌入反思——每轮 Action 后进行自我审视
  │  "我的搜索结果够全面吗？还需要补充什么信息？"
  │
Plan-and-Solve + Reflection
  │  在每个执行步骤后进行反思——帮助定位推导错误
  │  "这一步的计算逻辑正确吗？有没有遗漏的边界条件？"
  │
ReAct + Plan-and-Solve + Reflection（完整方案）
  │  规划 → (行动→反思→修正) → 最终答案
  │  
```

> **实践建议**：先单独掌握每种范式，再根据任务特点选择组合方式。Reflection 的"评审→改进"模式是提升输出质量的最通用手段，几乎可以叠加在任何 LLM 应用中。
